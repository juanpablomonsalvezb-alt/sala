01   Bloqueadores Críticos — No Puede Salir Sin Resolver Esto

1
Seguridad · Backend · Pagos
El webhook de MercadoPago acepta cualquier POST — sin validación de firma HMAC
Cualquier atacante puede hacer un POST a /api/mp/webhook con type: "payment" y un payment ID real, y el sistema activa suscripciones sin cobro real. MercadoPago envía una firma x-signature para validar autenticidad — el código actual no la lee ni la verifica. La variable MP_WEBHOOK_SECRET no existe en ningún archivo.
src/app/api/mp/webhook/route.ts
2
Infraestructura · Variables de Entorno
NEXT_PUBLIC_APP_URL=http://localhost:3001 — todos los webhooks y back_urls van a localhost
Esta variable se usa para construir la notification_url de MercadoPago (donde MP envía confirmaciones de pago) y el back_url (a donde redirige al usuario tras pagar). En producción, MP notificará a localhost:3001 — ningun webhook llegará al servidor real. El usuario paga y queda varado en una URL inexistente. Debe ser https://nebbuler.com en Vercel.
.env.local → Vercel Dashboard → Environment Variables
3
Frontend · Flujo del Lector
Las páginas de artículo dan 404 para 10 de 11 creadores — el flujo se rompe antes del paywall
[creator]/[post]/page.tsx no tiene fallback para los creadores estáticos de creators.ts. Solo el mock hardcodeado "rodrigo-fuentes" funciona. Los otros 10 creadores del home tienen perfiles que cargan, artículos con links visibles, pero al hacer clic en cualquier artículo: 404. El lector nunca llega al paywall ni al checkout.
src/app/[creator]/[post]/page.tsx
4
Backend · Seguridad
Políticas RLS duplicadas en sala_profiles — emails e is_superadmin son públicamente legibles
Hay dos políticas para sala_profiles SELECT: una restrictiva ("solo el propio usuario") y una permisiva ("visible para todos"). Supabase hace OR lógico — la permisiva gana. Cualquier usuario anónimo puede leer el email, avatar, y el flag is_superadmin de todos los usuarios de la plataforma.
supabase/migrations/ → políticas sala_profiles
5
Backend · Pagos
El webhook devuelve HTTP 200 aunque falle la escritura en BD — MercadoPago no reintenta
Cuando el upsert en sala_subscriptions falla (error de BD, anon key sin permisos), el webhook solo hace console.error y sigue devolviendo { received: true } con status 200. MercadoPago interpreta el 200 como entrega exitosa y no reintenta. El usuario pagó, el dinero salió, pero la suscripción nunca se activó. Silencioso e irrecuperable.
src/app/api/mp/webhook/route.ts — líneas 44-58
6
Backend · Variables de Entorno
SUPABASE_SERVICE_ROLE_KEY no confirmada en Vercel — webhook cae silenciosamente a anon key
El webhook usa SUPABASE_SERVICE_ROLE_KEY ?? NEXT_PUBLIC_SUPABASE_ANON_KEY. Si la service role key no está en Vercel (solo está en .env.local), el webhook usa la anon key. Con anon key, el upsert en sala_subscriptions falla por RLS sin lanzar excepción. Resultado: el webhook devuelve 200, MP no reintenta, suscripción no se activa.
src/app/api/mp/webhook/route.ts — línea 8
7
Frontend · Pagos
El botón dice "Suscribirse con Stripe" pero el backend usa MercadoPago
El checkout page muestra "Suscribirse con Stripe" en el CTA principal. El backend usa MercadoPago completamente (Stripe tiene placeholders). El usuario hace clic esperando ver Stripe y llega a MercadoPago — genera desconfianza activa en el momento de conversión más crítico.
src/app/suscribirse/[creator]/page.tsx → línea 184
8
Frontend · UX
El checkout no muestra ningún error al usuario cuando el pago falla
createCheckoutSession retorna { error: string } cuando falla (MP no configurado, usuario sin cuenta, creador no encontrado). Pero el formulario no captura ni renderiza ese retorno. El usuario hace clic en "Suscribirse" y nada pasa — sin mensaje, sin spinner, sin feedback. Flujo de pago completamente opaco.
src/app/suscribirse/[creator]/page.tsx → CheckoutForm
9
Dashboard · UX
La actividad reciente del dashboard es completamente falsa — ACTIVITY_MOCK hardcodeado
Todos los creadores ven exactamente la misma actividad ficticia: "Nueva suscripción activa hace 2h", "Publicación leída por 12 personas hace 5h". Son datos inventados. Si un creador real lo descubre, pierde confianza en toda la plataforma instantáneamente. En un mercado pequeño como Chile, eso se comunica rápido.
src/app/dashboard/page.tsx → ACTIVITY_MOCK
10
Frontend · Contradicción
El dashboard muestra "5% de comisión" — la landing dice "0% siempre"
La página de ingresos del dashboard calcula "Por cobrar · Después de comisión 5%". La landing pública, los FAQs, y el plan dicen explícitamente "0% de comisión — siempre." Contradicción directa que puede generar disputas legales y reputacionales desde el primer creador.
src/app/dashboard/ingresos/page.tsx → línea 64
11
SEO · Redes Sociales
Sin og:image en ninguna página — todos los links compartidos salen sin preview
No hay og:image en layout.tsx, en páginas de creadores, ni en artículos. Cada link compartido en WhatsApp, LinkedIn, Twitter o iMessage genera un preview vacío. Para una plataforma que depende del boca a boca y la viralidad de artículos, esto destruye el CTR de cada compartido antes del primer artículo indexado.
src/app/layout.tsx + generateMetadata en [creator] y [post]
12
Frontend · Ruta rota
/nueva-contrasena no existe — el flujo de recuperación de contraseña está roto
La recuperación de contraseña redirige al usuario a /auth/callback?next=/nueva-contrasena, pero esa ruta no está implementada en ningún archivo. El usuario llega a un 404 o a la home. No puede cambiar su contraseña.
Falta: src/app/nueva-contrasena/page.tsx
13
Dashboard · Funcionalidad
Editar publicación no funciona — el query param ?edit= es ignorado
El botón "Editar" en /dashboard/publicaciones linkea a /dashboard/nueva-publicacion?edit=${post.id}, pero esa página no lee ese parámetro ni carga el contenido existente. El creador abre un editor en blanco — todos sus artículos son ineditables después de publicarse.
src/app/dashboard/nueva-publicacion/page.tsx

02   Mapa del Flujo del Lector — Dónde se Rompe

Paso Acción del usuario Estado Problema
1 Llega a nebbuler.com Funciona Home carga, creadores visibles, navegación operativa.
2 Hace clic en un creador → perfil Funciona Fallback estático de creators.ts activo. Bio, artículos y precio visibles.
3 Hace clic en un artículo de pago Roto — 404 [post]/page.tsx no tiene fallback estático. 10 de 11 creadores dan 404. El lector nunca ve el paywall.
4 Hace clic en "Suscribirse" Roto URL de suscripción usa localhost. El botón dice "Stripe". El checkout no muestra errores al usuario.
5 Completa el pago en MercadoPago Roto notification_url y back_url apuntan a localhost:3001. Webhook nunca llega. Suscripción no se activa.
6 Regresa al sitio tras pagar Parcial Página /exito no verifica que el webhook llegó. Si no llegó, el usuario paga y sigue sin acceso.
7 Intenta leer el artículo pagado Roto Si el paso 3 da 404, nunca llega aquí. Si llega, la suscripción no se activó (paso 5 roto).
